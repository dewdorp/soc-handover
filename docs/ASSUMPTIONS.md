# ASSUMPTIONS.md — 가정 및 기본값 결정

> 요구사항에 명시되지 않아 **합리적 Default로 결정**한 사항 기록(§91).
> 각 항목은 사용자가 원하면 언제든 변경 가능하며, 변경 시 영향 범위를 함께 적었다.

---

## A. 환경 / 인프라

### A-01. PostgreSQL 미설치 환경 (실측 확인됨)
현재 PC에 PostgreSQL이 설치되어 있지 않고(`C:\Program Files\PostgreSQL` 없음, `psql` 없음, 서비스 없음),
시스템 Python/Node도 없다(codex 번들 런타임만 존재: Python 3.12.14 / Node 24.19.0).

**결정**
1. **운영 기본 DB는 PostgreSQL 16을 유지**한다(요구사항 §3). 스키마·인덱스·FTS 설계는 PG 기준.
2. `install.ps1`이 PostgreSQL을 탐지한다. 없으면
   - (a) 설치 안내(오프라인 설치 파일 경로 지정 가능), 또는
   - (b) **개발/평가 모드**로 SQLite를 사용해 즉시 구동(`DEV_DB=sqlite`).
3. SQLite 모드에서도 전 기능이 동작하도록 `search/backends/`를 방언별로 분리한다(FTS5 + LIKE).
   단, **운영 모드에서는 화면 상단에 상시 경고 배너**를 띄우고 `status.ps1`이 경고를 출력한다.
4. Alembic 마이그레이션은 방언 분기(`op.get_bind().dialect.name`)로 PG 전용 객체(tsvector/trgm, 부분 인덱스 일부)를 조건부 생성한다.

**영향**: 개발·시연은 즉시 가능, 운영 이관 시 `pg_dump` 대신 마이그레이션 + 데이터 이관 스크립트 1회 실행 필요.

### A-02. 런타임 경로
시스템에 python/node가 없으므로 스크립트는 다음 순서로 탐색한다.
`PATH` → `%LOCALAPPDATA%\Programs\Python\Python312` → codex 번들(`%USERPROFILE%\.cache\codex-runtimes\...`).
`.env`의 `PYTHON_EXE`, `NODE_EXE`로 명시 지정 가능.

### A-03. 포트
백엔드/통합 서비스 `8080`, 개발용 Vite `5173`. `.env`의 `APP_PORT`로 변경.

### A-04. OneDrive 경로
프로젝트가 OneDrive 동기화 폴더 안에 있다. `node_modules`, `.venv`, `data/`, `backup/`, `logs/`, `run/` 은
동기화 대상에서 제외(문서 안내 + `.gitignore`)한다. 대용량 첨부/DB의 클라우드 동기화 충돌을 피하기 위해
`data/`의 기본 경로를 `.env`의 `DATA_DIR`로 분리 가능하게 한다.

### A-05. 시간대
전 시스템 **Asia/Seoul 고정**. DB는 TIMESTAMPTZ(UTC 저장), 표시·경계 계산(오늘/이번주/교대)은 KST.
"이번 주"는 **월요일 시작**. 회계연도 개념 미적용.

## B. 업무 규칙

### B-01. 교대 정의 (§27) — **확정: 2교대** (2026-09-19 운영 확인)
처음에는 교대 시간이 없어 3교대(08/16/24)를 가정했으나 실제 운영은 주간·야간 2교대다.
```
DAY   주간 09:00 ~ 18:00
NIGHT 야간 18:00 ~ 다음날 09:00 (crosses_midnight, 15시간)
```
- 근무일(shift_date)은 **시작일** 기준. 9/17 03:00 은 9/16 야간이다.
- 관리자가 `PATCH /shifts/{id}` · `PUT /shifts`(교대표 전체)로 바꿀 수 있다. 저장 전에
  활성 교대가 하루 24시간을 **빈틈·겹침 없이** 덮는지 검사하고, 어긋나면 그 시각을 알려주며 거절한다.
- 목록에서 빠진 교대는 지우지 않고 비활성화한다(과거 인계 기록이 가리킬 수 있다).
  기존 설치의 SWING(오후)도 마이그레이션 `c4d2e8f1a9b3` 에서 비활성화만 했다.

"현재 근무 중 신규"는 현재 교대 시작시각 이후 등록된 건으로 판정한다.

### B-02. 재확인(Re-Ack) 트리거 필드 (§33)
기본값 = `title, content, work_date, status_code, priority_code, assignee_id`.
`system_settings['ack.reack_fields']` 로 관리자 변경 가능. 비고/태그/첨부 변경은 재확인을 유발하지 않는다.

### B-03. 확인(Ack) 시 기록 버전
**전달 시점 버전이 아니라 "확인 버튼을 누른 시점의 current_version_no"** 를 기록한다.
전달 당시 버전은 `shift_handover_items.version_no_at_transfer`에 별도 보존한다.
→ "확인 이후 변경" 판정은 `current_version_no > acked_version_no AND 재확인 대상 필드 변경`.

### B-04. 미완료(Open) 판정
`handover_statuses.category` 로 단일 판정한다.
`OPEN` = 신규/진행중/확인필요/조치예정 · `WAITING` = 대기/보류 · `CLOSED` = 완료/취소.
Carry Forward·지연·My Work·Cockpit 모두 이 분류를 사용한다(중복 정의 금지).

### B-05. 지연(Overdue) 정의
`work_date < 오늘` 이고 상태 category ≠ CLOSED. Task는 `due_date < 오늘` 기준.

### B-06. Carry Forward 자동 범위
직전 교대 세션의 항목 중 CLOSED가 아닌 것을 **다음 Basket의 후보로 자동 담되, 해제 가능**하게 한다.
완전 자동 전달(사용자 확인 없이 SENT)은 하지 않는다 — 인계는 사람의 명시적 행위여야 증적 가치가 있다.
받은 인계는 **한 번만** 이어 넘긴다. 받은 뒤 이미 인계를 보냈다면 다음 Basket 에는 자동으로 담지 않는다
(넘긴 건이 두 번 넘어가거나, 그때 일부러 뺀 건이 되살아나지 않게 — Phase 5 화면 확인에서 발견).

### B-07. 즐겨찾기 vs 상단고정
`★`(handover_stars)는 개인용, `상단고정`(is_pinned)은 전역용(MANAGER+). 목록 기본 정렬은
`is_pinned DESC → is_important DESC → registered_date DESC`.

### B-08. 삭제 권한
ANALYST는 삭제 불가(오등록 시 상태를 `취소`로 변경). Soft Delete는 MANAGER+, 물리 삭제는 제공하지 않는다.

### B-09. Handover 필수 입력
`company_id, title, content, registered_date, status_code, priority_code`. 그 외는 선택.
Excel Import 시에는 `title`이 없으면 `content`의 첫 60자를 제목으로 생성하고 `title_auto_generated=true`를
`raw`에 기록한다(원본 Excel에 제목 컬럼이 없기 때문 — §45).

### B-10. 관계사/인명 마스터 매칭
Import 시 자동 생성 OFF가 기본. 매칭 실패해도 `*_name_raw` 텍스트로 100% 보존하므로 데이터 손실 없음.
후속으로 관리자 화면에서 "미매핑 인명 일괄 연결" 도구를 제공한다(Phase 8).

### B-11. 할일(Task) 규칙 (Phase 6)
- 할일은 인수인계(사실)와 분리된 '해야 할 일'. 인수인계에 연결해도 할일 변경이 인수인계 버전을 올리지 않는다.
- 수정·보드 이동은 `expected_version` 필수(인수인계와 같은 §26 원칙). 체크리스트·댓글은 버전을 올리지 않는다.
- 고칠 수 있는 사람: 만든 사람·담당자, 또는 MANAGER+(`task:update_any`). 지우기: 만든 사람 또는 MANAGER+.
  삭제는 표시만(`is_deleted`). 담당자를 비우면 만든 사람이 담당자다.
- 상태: 할일 · 진행중 · 대기 · 완료 · 취소. 완료로 가면 `completed_at` 기록, 완료에서 벗어나면 지운다.
  보드에는 취소 칸이 없다(상세에서 취소). 완료 칸은 최근 14일 완료분만 보인다.
- 보드 위치는 '어느 카드 바로 뒤'(`after_id`)로 받는다. 담당자로 걸러진 보드에서 옮겨도 전체 순서가 맞다.
- 감사: 생성·수정·완료·삭제. 보드 이동은 **상태가 바뀔 때만** 기록(같은 칸 안의 순서는 업무 이력이 아님).
- 알림: 다른 사람이 나를 담당자로 지정하면 `TASK_ASSIGNED`, 내 할일(만든·담당)에 남이 댓글을 달면 `TASK_COMMENT`.
- 인수인계에서 바로 만들기: 비운 칸은 인수인계의 관계사·제목·내용 앞 500자·중요도로 채운다.
- 목록 조건은 인수인계 DSL 이 아니라 정해진 조건(검색어·상태·담당·관계사·연결 인수인계·마감)만 받는다.
  할일 건수는 인수인계만큼 많지 않고, 열린 필드 DSL 을 늘리면 SQLi 방어 면적만 커진다.
- 첨부는 인수인계 첨부와 함께 뒤 Phase 에서(첨부 기능 자체가 아직 없다).

### B-12. 내 업무(My Work) 버킷 (Phase 6)
- 모으는 것: 내가 담당인 할일, 내가 담당인 인수인계, 내가 확인할 인수인계(인수 확인함). 일정은 Phase 7.
- 기준일: 할일은 마감일, 인수인계는 수행일. 확인할 건은 날짜 없음.
- 지연 = 기준일 < 오늘, 오늘 = 오늘, 이번주 = 오늘 ~ 이번 주 일요일(월요일 시작), 예정 = 다음 주 이후,
  확인필요 = 인수 확인함, 대기 = 할일 WAITING · 인수인계 분류 WAITING, 완료 = 최근 7일 안에 끝낸 것.
  완료 외 버킷은 안 끝난 것만. 한 건이 여러 버킷에 들 수 있다(오늘 마감은 이번주에도).
- 정렬: 지연 먼저 → 기준일 빠른 순(날짜 없는 것은 뒤) → 중요도.
- 버킷 건수는 고른 출처(전체/할일/인수인계/확인) 기준으로 센다.
- 일정(Phase 7)은 오늘부터 30일 안에서 일정마다 가장 가까운 회차 **하나**만 넣는다(매일 반복이 목록을 채우지 않게).
  일정은 지나면 목록에서 빠진다 — 일정에는 지연·완료가 없다.

### B-13. 일정(Schedule) 규칙 (Phase 7)
- 시각은 시간대를 붙여 주고받는다. 시간대가 없으면 KST. 끝(end_at)은 포함하지 않는다.
- 끝을 비우면 1시간. 하루 종일이면 시작일 00:00 ~ 마지막 날 다음 날 00:00 으로 맞춘다.
  일정 하나는 31일을 넘지 않는다(길게 이어지는 일은 반복으로).
- 인수인계·할일에 연결해 만들면, 비운 제목·관계사는 그쪽 값으로 채운다. 담당(owner)을 비우면 만든 사람.
- 고칠 수 있는 사람: 담당자·만든 사람, 또는 MANAGER+. 수정·달력 이동은 `expected_version` 필수(§26).
  시작만 바꾸면 길이를 유지한다. 삭제는 표시만.
- 감사: `CALENDAR_CREATE / CALENDAR_UPDATE / CALENDAR_DELETE`. 달력 끌어놓기는 이전·이후 시각과 `via=drag`.
- 알림: 남이 나를 담당자로 지정하면 `SCHEDULE_ASSIGNED`.
- 반복: RRULE 부분집합 — `FREQ=DAILY|WEEKLY|MONTHLY`, `INTERVAL` 1~99, `BYDAY`(매주만), `COUNT` 1~500 또는
  `UNTIL`(날짜, 그날 끝까지). 다른 키는 거절한다. 한 건으로 저장하고, 조회할 때 기간 안의 회차만 펼친다
  (한 번에 최대 400회). 매월 31일 같은 날이 없는 달은 건너뛴다(dateutil 규칙 그대로).
- **회차 하나만 옮기거나 지우는 예외는 지원하지 않는다.** 반복 일정은 달력에서 끌 수 없고, 상세에서 시리즈 전체를
  고친다. 교대 점검처럼 규칙적인 일에 예외가 잦으면 그때 예외 테이블을 둔다(G 절 참고).
- 달력은 일정 + 할일 마감일 + 인수인계 수행일을 레이어로 겹친다. 할일·인수인계는 하루 종일 표시이고 달력에서
  옮기지 않는다(마감·수행일은 각 상세에서 바꾼다). 한 번에 볼 수 있는 기간은 100일, 이벤트는 2,000건까지.
- 화면(달력·일정 창)은 브라우저 시간대가 KST 라고 가정한다(A 절 'Asia/Seoul 고정'과 같은 전제). 서버와는 +09:00 을 붙여 주고받는다.

### B-14. 감사 조회 · 댓글 · 첨부 · 알림 (Phase 8)
- **감사 조회**: 기간 필수, 최대 93일. ANALYST 는 자기 행위만(`audit:read_self`), MANAGER+ 전체. 내보내기(xlsx)도
  `EXCEL_EXPORT`(resource_type=AUDIT)로 남는다. 감사 로그는 앱에서 읽기만 한다.
- **감사 34종**: 정의된 행위 전부가 실제로 기록된다(테스트로 강제). 완료 기준 '30종 이상' 충족.
  (처음 35종에서 AI 켬·끔 2종은 AI 제외로 뺐고, Phase 10 에 감사로그 보관 정리 1종을 더했다)
- **인수인계 댓글**: 본문 버전을 만들지 않고 재확인도 일으키지 않는다. 고치기는 쓴 사람, 지우기는 쓴 사람·MANAGER+,
  지우기는 표시만. 쓰기·고치기·지우기 모두 `HANDOVER_COMMENT`(detail.op), 고치기는 이전 글을 before 에.
- **첨부**: 허용 확장자·최대 크기는 관리 설정. 실행·스크립트 형식(exe·ps1·html·svg 등)은 허용 목록에 넣을 수도 없다.
  저장은 무작위 이름·확장자 없이, 원래 이름은 DB 에만. 크기는 받으면서 센다. 올리기·지우기는 대상을 고칠 수 있는 사람
  (지우기는 올린 본인도), 받기는 모든 역할. 지우기는 표시만 하고 파일은 남긴다(증적). 올리기·받기·지우기 모두 감사.
  백신 연동은 `.env` 의 `ATTACHMENT_SCAN_COMMAND` — 비우면 검사 안 함(NOT_SCANNED), 있으면 종료코드 0 만 통과,
  실행 실패도 거절(안전한 쪽).
- **그림 미리보기**: 화면 캡처를 내려받지 않고 그 자리에서 본다. 그림인지는 **파일 내용**(앞부분 바이트)으로만
  판단한다 — 이름·확장자를 믿고 inline 으로 내보내면 내용이 HTML 인 `x.png` 을 브라우저가 실행할 수 있다.
  PNG·JPEG·GIF·WEBP·BMP 만 내보내고 SVG 는 제외한다(애초에 올리지도 못한다).
  `nosniff` 와 `CSP: default-src 'none'; sandbox` 를 함께 보낸다.
  **미리보기는 감사에 남기지 않는다** — 인수인계 화면을 여는 것과 같은 행위이고, 그림 하나에 요청이 여러 번
  가므로 남기면 감사로그가 이것으로 찬다. 파일을 손에 넣는 '받기'는 그대로 `ATTACHMENT_DOWNLOAD` 로 남는다.
- **알림 7종(ERD §66) 대응**: HANDOVER_ASSIGNED(담당 지정) · ACK_REQUIRED → `HANDOVER_TRANSFER`(인계 받음) ·
  CHANGED_AFTER_TRANSFER → `HANDOVER_REACK`(재확인 필요) · TASK_ASSIGNED · TASK_DUE_SOON(마감 오늘·내일) ·
  TASK_OVERDUE(마감 지남) · IMPORTANT_HANDOVER(중요 표시·긴급 → MANAGER+ 에게). 여기에 TASK_COMMENT · SCHEDULE_ASSIGNED 가 더 있다.
  마감 알림은 서버 안에서 `REMINDER_INTERVAL_MIN`(기본 30분)마다 돌고, 할일마다 **하루 한 번**(읽어도 다시 오지 않음).
- **통계**: MANAGER+(`stats:read_all`). 기간 최대 366일. 확인율은 기간 안에 보낸 교대 인계 항목 중 받는 사람이 확인한 비율,
  걸린 시간은 전달 → 그 사람의 (마지막) 확인 시각이라 재확인이 있으면 길게 나올 수 있다.
- **백업·복구**: `backup.ps1` · `restore.ps1` 이 서버에 `BACKUP` · `RESTORE` 감사를 남긴다(로컬에서만 받는 경로).
  웹에서 복구는 하지 않는다 — 복구는 서버를 멈추고 하는 작업이다.
- **감사로그 보존(`retention.audit_days`, 최소 365일)** (Phase 10): 매일 백업(`backup.ps1`) 직후 `manage.py archive-audit` 이
  기간이 지난 감사로그를 `backup/audit-archive/audit_before_*.jsonl.gz`(+ .sha256)로 **먼저 내보내고, 다시 읽어 건수를 확인한 뒤**
  DB 에서 지운다. 이 정리도 `AUDIT_ARCHIVE` 로 감사에 남는다. 지워진 행은 그날 DB 백업에도 들어 있고, 보관 파일은 지우지 않는다.
  앱이 감사로그를 지우는 유일한 경로다(SECURITY §감사).
- **설정 화면**: 서버가 준 입력 규칙(spec)대로 그리고 검사도 서버가 한다. 비밀 값(`is_secret`)은 `.env` 에서만 바꾼다.

### B-16. 장비 비밀번호 보관 (현장 요청)

관계사 장비의 접속 계정 · 비밀번호를 한 곳에 둔다. 서버에 두는 이상 **암호화가 전제**다.

- **암호화**: AES-256-GCM. 항목마다 무작위 nonce, 인증 태그로 변조 탐지, AAD 로 항목 id 를 묶어
  다른 항목의 암호문을 옮겨 붙이는 것도 막는다. 키는 `.env` 의 `VAULT_KEY`(base64 32B) —
  DB 에는 키가 없으므로 덤프만으로는 읽히지 않는다. 자세한 것은 docs/SECURITY.md §7.1.
- **키를 잃으면 복구 불가**: DB 백업에는 암호문만 들어간다. `.env` 를 따로 보관하라고 운영 문서에 적었고,
  백업 안내에도 넣었다. 키를 바꿔 끼우면 조용히 깨진 값이 나오는 게 아니라 **복호화가 실패**한다.
- **직접 구현하지 않는다**: 파이썬 표준 라이브러리에 AES 가 없어 `cryptography` 를 넣었다.
  그 대가로 이 버전은 앱만 바꾸는 패치가 아니라 전체 패키지로 배포해야 한다(라이브러리가 바뀐다).
- **범위**: 항목마다 SHARED(교대 근무자 전원) · PERSONAL(등록자만) 중 하나. 남의 PERSONAL 은
  목록에도 없고 id 를 알아도 404 — 있다는 사실 자체를 감춘다. 고치기 · 지우기는 등록자와 MANAGER+
  (인수인계 · 할일과 같은 규칙).
- **열람**: 볼 때마다 **본인 계정 비밀번호를 다시 확인**하고(자리를 비운 사이 남이 여는 것을 막는다),
  한 건씩 감사에 남긴다. 실패한 시도도 남는다(CREDENTIAL_REVEAL_DENIED). 화면은 1분 뒤 저절로 닫힌다.
- **변경 이력**: 바꾸기 전 값을 암호문으로 최근 5개까지 남긴다 — 새 비밀번호가 장비에 안 먹었을 때
  되돌려야 하기 때문. 그보다 오래된 이력은 '누가 언제 무엇을 바꿨나'만 남기고 값은 지운다.
- **검색 · 내보내기**: 장비명 · 계정 · 접속 방법만 찾을 수 있다. 비밀번호는 암호문이라 검색 대상이 아니고,
  Excel Export 에도 이 표는 들어가지 않는다.

### B-15. 배포 · 성능 결정 (Phase 10)
- **오프라인 설치 패키지**: 인터넷 없는 PC 에 Python 3.12 · PostgreSQL 16 · VC++ 런타임까지 담아 zip 하나로 준다
  (INSTALL_WINDOWS.md A장). 설치 위치는 영문 · 공백 없는 경로, DB 는 127.0.0.1 전용, 데이터 · 백업 · 로그 ·
  .env 는 관리자와 설치한 사용자만 읽는다. 기본은 서비스 모드(부팅 시 자동 시작 · 매일 03:00 백업 · 방화벽),
  `-Manual` 은 수동 실행.
- **DB 초기화 값**: UTF8 · 로케일 C(Windows 지역 설정과 무관하게 같은 정렬, 한글은 유니코드 순서 = 가나다 순),
  `lc_messages=C`(로그는 영어), data-checksums 켜고, shared_buffers 는 RAM 에 따라 256MB~1GB.
- **Smart App Control(Windows 11)**: 켜져 있으면 서명 없는 PostgreSQL 실행 파일이 막힌다(실측). 설치 프로그램이
  미리 확인하고 멈춘다 — 끄거나, 사내 인증서로 서명하거나, 꺼진 PC 에 설치한다.
- **질의는 `= false` 로 쓴다**: `IS false` 는 PostgreSQL 이 부분 인덱스 조건(`WHERE ... = false`)과 같다고
  증명하지 못해 인덱스를 통째로 놓친다(0.14ms → 133ms). SQLite 에서는 차이가 없어 드러나지 않으므로
  **PostgreSQL 로도 전체 테스트**를 돌린다(TEST_DATABASE_URL).
- **계획 캐시**: PG 연결마다 `plan_cache_mode = force_custom_plan`. 검색은 조건 값에 따라 좋은 계획이 달라서
  굳은 계획(generic plan)이 인덱스를 놓친다.
- **Cockpit**: 목록은 보고 있는 영역만 만들고(`?area=`), 타일 숫자는 9,999 까지만 센다(넘으면 `9,999+`).
- **성능 기준 통과**: 50만 건에서 가장 느린 화면 p95 356ms(docs/PERFORMANCE.md).

## D. 이관 (Excel)

### D-01. 원본 파일
현재 `C:\Users\dewdrop\OneDrive\인수인계` 폴더는 비어 있어 실제 Excel을 확인하지 못했다.
따라서 §45의 8개 컬럼을 기준으로 **관대한 매핑기**를 구현하고, 헤더 이름 변형(공백·괄호·유사어)을
사전으로 흡수한다. 실제 파일 확보 시 매핑 사전을 보강한다(코드 수정 없이 설정으로 추가 가능하게 설계).

### D-02. 중복 Fingerprint
`sha256( norm(관계사) | 날짜(YYYY-MM-DD) | norm(내용 앞 500자) | norm(전달자) )`.
`norm` = 공백 정규화 + 소문자화 + 특수문자 제거. 중복 판정은 **의심 표시만**, 삭제·자동 병합 없음(§48).

### D-03. 날짜 파싱
Excel serial, `YYYY-MM-DD`, `YYYY.MM.DD`, `MM/DD`, `9월 16일`, `26-09-16` 등을 허용.
연도 없는 값은 Sheet 이름의 연도를 보완값으로 사용하고 `date_inferred=true`를 raw에 기록한다.

### D-04. Import 시 작성자
`created_by` = Import 실행 관리자, `sender_name_raw` = 원본 전달자 문자열.
v1 버전의 `changed_by`도 실행 관리자이며 `change_reason`에 job 코드를 남긴다(증적 명확화).

### D-05. 진행상황이 비었거나 모를 때의 상태 (Phase 4)
기본 `DONE`(완료). 마법사에서 바꿀 수 있다.
과거 Excel 기록은 대부분 끝난 일이다. 미완료로 넣으면 수천 건의 오래된 항목이 '미완료'·'지연'
목록을 채워 **진짜 남은 일이 묻힌다** — 그 자체가 누락이다. 모르는 값은 경고로 표시해 사람이 본다.

### D-06. '한 필드에 컬럼 하나' 는 Sheet 단위 (Phase 4)
연도별 Sheet 마다 헤더 표기가 다를 수 있다(2024 `진행상황`, 2025 `진행 상황`).
파일 전체 기준으로 제약하면 두 번째 Sheet 의 상태 컬럼이 매핑에서 빠진다. Sheet 안에서만 겹치지 않으면 된다.

### D-07. 등록되지 않은 관계사 (Phase 4)
값 매핑에서 (a) 기존 관계사 연결 (b) 새로 등록 (c) 그대로 중 고른다. 기본은 (c).
(c) 는 '미지정' 관계사로 들어가고 **원래 이름을 비고 맨 앞에 `[원본 관계사: X]` 로 남긴다**
(관계사 원문 컬럼이 없으므로). 비고는 통합 검색 대상이라 원래 이름으로도 찾을 수 있다.

### D-08. 중복 의심 · 오류 행의 기본 처리 (Phase 4)
- 오류 행: 가져올 수 없다. 사용자가 '가져오기'를 골라도 들어가지 않는다.
- 중복 의심: 기본 제외. 사람이 '가져오기'를 고른 경우에만 들어간다.
  같은 파일을 두 번 올려 전부 두 벌이 되는 사고를 막는다.
- 둘 다 **지우지 않는다**. staging 에 남아 있고 목록·실패행 Excel 로 확인할 수 있다.
- UI 로 등록한 건도 같은 식으로 지문을 계산한다. Excel 에 이미 입력해 둔 건을 알아볼 수 있어야 한다.

### D-09. Import 되돌리기 (Phase 4)
job 단위 Soft Delete. 단 **가져온 뒤 누군가 수정한 건(current_version_no > 1)은 지우지 않는다.**
되돌리기로 남의 작업을 날리면 그게 누락이다. 몇 건을 남겼는지 결과에 표시한다.

### D-10. Export 상한 (Phase 4)
`export.max_rows`(기본 100,000)를 넘으면 **잘라서 주지 않고 거부**한다. 잘린 파일을 받은 사람은
그게 전부인 줄 안다. 조건을 좁혀 나눠 받게 한다. 셀은 전부 문자열로 써서 수식 주입을 막는다.

### D-11. 백그라운드 작업과 재기동 (Phase 4)
Import 의 긴 단계는 요청 응답 뒤 같은 프로세스에서 돈다(F-03 단일 프로세스 전제).
재기동하면 RUNNING 으로 남은 작업을 FAILED 로 정리하고 멈춘 단계(phase)를 남긴다.
COMMIT 은 행 단위 멱등이라 다시 실행하면 남은 행만 들어간다.
**다중 워커로 늘릴 때는** 이 정리 로직이 다른 워커의 작업을 실패로 만들 수 있으므로 작업 소유자 표시가 필요하다.

## F. 기술 선택

### F-01. Data Grid
**TanStack Table v8(headless) + 자체 셀 렌더링 + `@tanstack/react-virtual`** 을 사용한다.
요구된 기능(서버 페이징/필터/정렬/리사이즈/리오더/가시성/선택/키보드/대용량)을 모두 충족하면서
유료 라이선스 의존이 없다(AG Grid Enterprise 회피 §3).

### F-02. Calendar
FullCalendar(MIT 코어, 월/주/일 + DnD) 사용. 상용 플러그인 미사용.

### F-03. 백그라운드 처리
Celery/Redis를 도입하지 않는다(Windows 단일 노드에 과함). **APScheduler + DB 기반 Job 테이블**로
Import/스윕을 처리하고, 프론트는 폴링한다.

### F-04. 실시간성
WebSocket을 도입하지 않는다. 알림·충돌 감지는 30초 폴링(`/notifications/unread-count`,
Drawer 열림 시 대상 handover의 `current_version_no`). 필요 시 Phase 10에서 SSE로 승격.

### F-05. 패키지 관리
백엔드는 `pip + requirements.txt`(버전 고정). 프론트는 **npm 우선, 없으면 pnpm** 순으로 자동 선택한다
(`Resolve-PackageManager`). 현재 이 PC에는 npm이 없고 번들 pnpm만 있어 pnpm 경로로 검증했다.
pnpm 사용 시 esbuild 네이티브 바이너리 설치 스크립트를 허용해야 하므로 `frontend/pnpm-workspace.yaml`에
`allowBuilds: { esbuild: true }`를 둔다(npm 사용 시 이 파일은 무시된다).
오프라인 설치는 사전 다운로드한 wheel/`node_modules` 사용 절차를 `INSTALL_WINDOWS.md` §6에 문서화했다.

### F-06. 프로세스 종료 시 자식 프로세스 정리 (Phase 1 실측)
일부 Python 배포판(이 PC의 번들 런타임 포함)에서는 venv의 `python.exe`가 실제 서버를 **자식 프로세스로**
띄운다. 부모 PID만 종료하면 포트가 계속 물려 있어 재기동이 실패하므로, `stop.ps1`은
(1) PID 파일의 프로세스와 그 자식들을 함께 종료하고 (2) 종료 후에도 포트가 LISTEN 이면 점유 프로세스를
추가로 정리한 뒤 (3) 그래도 남아 있으면 경고를 출력한다.

### F-07. 운영 스크립트의 접속 주소
`.env`의 `APP_HOST=0.0.0.0`은 **바인딩 주소**이지 접속 주소가 아니다. `backup.ps1`/`status.ps1` 등이
자기 자신을 호출할 때는 `127.0.0.1`로 정규화한다(`Get-ApiBaseUrl`). 감사 기록용
`POST /api/v1/audit/system-event`는 loopback 에서만, 허용된 Action(BACKUP/RESTORE)만 받는다.

## H. 1.3.0 에서 기본값으로 정한 것

요구사항에 없어 기본값으로 둔 것들. 전부 관리자 화면이나 설정으로 바꿀 수 있다.

### H-01. 근무표 기준일 — `roster.epoch_date` = 2026-01-05 (월요일)
16일 주기의 0일째를 어디에 놓을지는 현장의 실제 근무표를 봐야 정해진다. 설치 직후에는
월요일로 두고, 관리자가 `POST /roster/epoch` 로 바꾼다. 바꿀 때 32일치가 '매일 주간 1조 ·
야간 1조'인지 확인하고 아니면 저장하지 않는다.

### H-02. 조 정원 — `roster.team_size` = 4명
4조 × 4명 = 16명을 가정했다. 이 값보다 적게 서면 '결원'으로 표시한다. 조마다 인원이 다르면
이 값은 '최소 인원'의 뜻으로 쓰인다(조별 정원은 아직 지원하지 않는다).

### H-03. 조의 주기 위치 — A·B·C·D = 0 · 4 · 8 · 12
4일씩 밀면 매일 주간 1조 · 야간 1조가 된다. 조 이름(1조~4조)과 묶음은 관리자가 바꾼다.

### H-04. 새 계정의 열람 그룹 — **없음**
관리자가 넣기 전까지 자기가 쓴 글과 자기가 당사자인 글만 본다. '새 사람에게 과거 자료가
자동으로 열리지 않는다'를 기본으로 택했다. 반대(기본 그룹 자동 배정)를 원하면 사용자 등록
화면에서 그룹을 함께 고르게 바꾸면 된다.

### H-05. 업무의 기본 공개 범위 — 쓴 사람의 **기본 그룹**
'전체 공개'는 손으로 골라야 한다. 비워 두고 올리면 기본 그룹이 들어간다.

### H-06. 일정 알림 선택지 — 끄기 · 시작할 때 · 10분 전 · 30분 전 · 직접(0~7일)
현장에서 쓰는 값이 다르면 PRESETS 만 바꾸면 된다. 알림은 할일 마감 알림과 **같은 주기**로
돌고(`REMINDER_INTERVAL_MIN`), 2시간 넘게 지난 것은 보내지 않는다.

### H-07. 교대 마감 점검의 다섯 줄
확인하지 않은 인계 · 보내지 않은 바구니 · 내 담당 미완료 · 지연 · 다음 근무 결원.
현장에서 '이건 왜 없냐'가 나오면 `shift_service.closing_check()` 에 줄을 더한다.

### H-08. 로그인 상한 — `RATE_LIMIT_LOGIN_PER_5MIN` = 20 (5분 · IP 기준)
한 PC 를 여럿이 돌려 쓰는 교대 콘솔에서 교대 시각에 모자랄 수 있다. 현장에서 '로그인이
막힌다'는 말이 나오면 이 값을 올린다(SECURITY §8-1).

### H-09. RAG 색인 계정
색인을 만드는 계정이 어느 그룹에 속하는지가 곧 색인의 범위다. 전용 계정을 두고 그 계정의
그룹을 운영 규정으로 정하는 것을 전제했다([RAG.md](RAG.md) §3).
