## 3. 무엇이 문제였고 무엇을 고쳤나

### 3.1 부분 인덱스가 전부 무시되고 있었다 (가장 큰 원인)

앱은 `is_deleted IS false` 로 질의했는데 인덱스 조건은 `WHERE is_deleted = false` 다.
PostgreSQL 은 이 둘이 같다는 것을 증명하지 못해 **모든 부분 인덱스를 쓰지 않고 전체를 훑었다.**

```
WHERE is_deleted IS false  → Parallel Seq Scan   133ms
WHERE is_deleted = false   → Index Only Scan     0.14ms   (같은 질의, 950배)
```

→ 서비스 · 리포지토리 57곳의 `.is_(False)` · `.is_(True)` 를 `== false()` · `== true()` 로 바꿨다.
SQLite 에서는 차이가 없어 개발 중에는 드러나지 않는다 — **PostgreSQL 로도 테스트**해야 보이는 종류의 문제다.

### 3.2 같은 질의를 6번 넘게 실행하면 계획이 굳는다

psycopg 는 반복되는 질의를 준비된 구문(prepared statement)으로 만든다. PostgreSQL 은 여섯 번째부터
값과 무관한 '일반 계획'으로 바꾸는데, 검색은 조건 값에 따라 좋은 계획이 완전히 달라서
검색어 인덱스를 못 쓰게 됐다(한글 검색 270ms → 2.5초, 최악 35초).

→ PG 연결마다 `SET plan_cache_mode = force_custom_plan` (app/core/db.py). 계획 비용은 질의당 ~1ms.

### 3.3 목록 기본 정렬을 덮는 인덱스가 없었다

기본 정렬은 `상단고정 ↓ · 등록일 ↓ · id ↓` 인데 이 순서를 덮는 인덱스가 없어 50만 건을 정렬한 뒤
50건을 잘라 썼다. → 마이그레이션 `b3f1a7c9d240` 이 `ix_ho_list_sort` 를 추가한다.

### 3.4 같은 건수를 두 번 셌다

목록 응답은 '검색결과 수'와 '전체 수'를 함께 주는데, 조건이 없을 때도 둘을 따로 셌다.
→ 조건이 없으면 한 번만 센다(같은 값이다).

### 3.5 Cockpit 이 보이지도 않는 영역의 목록까지 만들었다

교대 Cockpit 은 영역 6개의 건수와 목록을 모두 만들었지만 화면에는 고른 영역 하나만 보인다.
또 '지연 17만 건' 같은 숫자를 정확히 세는 데만 0.6초가 걸렸다.
→ 목록은 **보고 있는 영역만**(`GET /shift-handovers/cockpit?area=…`), 나머지 타일 숫자는 9,999 까지만
세고 넘으면 `9,999+` 로 보여 준다.

## 4. 남은 것 · 참고

- **운영 PC 사양**이 이 개발 PC 보다 낮으면 그만큼 느려진다. 설치 후 `status.cmd` 로 DB 크기를,
  체감이 느려지면 `data\pgdata\log` 의 느린 질의를 본다.
- 이번 측정은 **한 사람 기준**이다. NFR-05(동시 20~50명)는 uvicorn 1프로세스 + PG 연결 10개로 잡혀 있어,
  실제 동시 사용이 많아지면 `.env` 의 `SQL_POOL_SIZE` 와 워커 수를 함께 올려야 한다.
- 검색어가 **2글자 이하**면 trigram 인덱스를 쓸 수 없어 느리다(설계상 감수 — 놓치는 것보다 낫다).
- 측정 데이터는 한 문장에 같은 낱말이 반복되는 합성 데이터라, 실제 데이터보다 **검색이 불리한** 조건이다.
